# orchestration 规格增量

## ADDED Requirements

### Requirement: R-orchestration-001 持久化恢复
控制平面的计划执行必须持久记录工作、控制流版本和步骤运行；进程中断后从未完成的步骤继续，已完成步骤不得重复执行。系统步骤与 agent 步骤的中断恢复不得依赖内存状态。控制流验收必须使用真实 DBOS 与 Postgres；外部系统、规划 agent 与执行器可按测试方案使用桩，该证据不代表真实执行器交付。
#### Scenario: R-orchestration-001.S1 步骤中断后恢复
- GIVEN 一项工作已有完成的步骤，当前 agent 步骤尚未完成
- WHEN 杀死执行进程并在同一持久化状态上重启
- THEN 从中断步骤继续，已完成步骤的执行次数不增加，工作和步骤记录可连续追溯

### Requirement: R-orchestration-002 对外动作幂等
对外动作必须先记录再执行，失败按退避重试。每次动作必须使用由工作、段、步骤与步骤定义哈希确定的幂等键；外部系统不支持幂等键时必须先查询该动作是否已完成。不得把持久化步骤至少执行一次误作外部效果恰好一次保证。
#### Scenario: R-orchestration-002.S1 外部效果已发生时崩溃
- GIVEN 分别支持和不支持幂等键的外部系统，动作效果已经发生而步骤检查点尚未记录
- WHEN 杀死进程后恢复并重试该步骤
- THEN 两种外部系统均只保留一次动作效果；前者复用同一键，后者查询到已完成动作而不重复创建

### Requirement: R-orchestration-003 重规划结果与动作键沿用
新计划版本中定义未变且上游未重跑的步骤必须沿用原结果与幂等键；定义改变或上游重跑的步骤必须重新执行，定义改变时使用新动作键。正在执行的步骤先完成，其结果保留在原版本记录中；重新规划不能抹去已发生的对外动作。
#### Scenario: R-orchestration-003.S1 指令后的步骤复用
- GIVEN 可信指令触发新版本，其中有定义未变、定义改变和上游重跑的步骤
- WHEN 当前步骤结束并执行新版本
- THEN 未变且上游未重跑的步骤不重执行并沿用结果和键；改变定义的步骤用新键重跑；上游重跑的步骤重新执行，旧版本结果仍可追溯

### Requirement: R-orchestration-004 人工关卡持久等待
人工关卡必须按授权记录等待指定角色，执行职责分离检查；等待状态必须持久化且不得占用用于实际执行步骤的工作队列名额。重启不能丢失关卡、接受无权评审或使独立评审退化为触发人单独批准。
#### Scenario: R-orchestration-004.S1 等待跨重启且不阻塞其他工作
- GIVEN 一项工作停在要求独立评审的人工关卡，另有就绪工作
- WHEN 重启进程，提交另一工作，并依次收到触发人单独批准和有效评审人的批准
- THEN 原工作保持等待直到有效评审；另一工作可以执行；无效批准不推进关卡且有审计记录

### Requirement: R-orchestration-005 关卡时限与消息隔离
每个关卡必须有明确等待时限，默认值来自处理流程；截止时间持久保存，重启后不重新计时。到期必须按流程先提醒再升级。每个关卡使用自己的评审消息主题，其他关卡的消息不能被消费后丢失或错误推进当前关卡。
#### Scenario: R-orchestration-005.S1 原截止时间与独立主题
- GIVEN 两个关卡有不同评审消息主题和已保存的缩短截止时间
- WHEN 等待中重启，向其中一关卡发送评审，并跨过另一关卡的原截止时间
- THEN 评审只推进目标关卡；未处理关卡按原截止时间提醒并升级，重启不延后期限，各次提醒与升级可追溯

### Requirement: R-orchestration-006 声明式计划执行前校验
计划必须是声明式数据，只能使用目录中登记的步骤及允许参数，包含依赖、引用输入、输出类型和有界失败处理，不得执行任意代码或无界循环。执行前必须校验结构、权限、预算、规格覆盖与关卡：输入来自祖先步骤且类型匹配；权限和数据范围不超授权与安全策略；成本含重试且受各层剩余预算与强制上限约束，个人订阅按既定规则免计金额；任务与步骤双向覆盖；规定关卡齐全且有时限。失败必须指出校验项和相关步骤，零步骤执行。
#### Scenario: R-orchestration-006.S1 不合格计划全部拦截
- GIVEN 五类校验各一份不合格计划，另有非祖先输入和关卡无时限的计划
- WHEN 提交各计划执行
- THEN 全部在任何步骤执行前拒绝，错误指出校验项及适用的步骤；仅为间接祖先的合法同型输入不会被当作错误

### Requirement: R-orchestration-007 校验与解释一致
校验通过的计划必须能被解释器接受，并推进到完成或合法人工关卡；校验拒绝的计划不得执行任何步骤。不得出现校验允许而解释器因未支持的计划结构、步骤配置或引用规则无法执行的情况。
#### Scenario: R-orchestration-007.S1 随机计划验证一致性
- GIVEN 使用 fast-check 生成的包含合法与非法结构、依赖、输入引用和关卡的计划集及可控外部桩
- WHEN 对每份计划先校验，再向解释器提交
- THEN 校验通过的计划均结束或停在合法关卡；校验拒绝的计划执行步骤数均为零

### Requirement: R-orchestration-008 缓存与结构稳定性
计划缓存键必须包括处理流程版本、规格结构中的任务编号、执行环境模板版本与策略版本，不包含规格措辞；命中时复用首次生成的计划并绑定参数，不再调用规划 agent。结构签名由步骤类型、目录步骤、对应任务、关卡角色与依赖构成，与步骤编号无关。规划 agent 只选择结构；重试、等待时限由目录或流程提供，配置只能选允许值。
#### Scenario: R-orchestration-008.S1 命中复用与结构变化
- GIVEN 相同缓存键的多项工作，以及仅措辞或步骤编号改变的等价输入
- WHEN 连续规划这些工作，再提交任务结构改变的规格
- THEN 相同键仅首次调用规划桩并复用首次计划，措辞不改变键、步骤编号不改变结构签名；任务结构改变导致未命中并重新规划

### Requirement: R-orchestration-009 有界重规划
校验失败重试、规格变化、可信指令及 agent 请求重新规划必须受每项工作的重新规划上限约束，默认上限为三次。校验通过的计划不可修改，变化必须形成带原因与依据的新版本并重新校验；超过上限必须转为需人处理，不再自动继续规划或执行未通过校验的版本。
#### Scenario: R-orchestration-009.S1 超过默认上限
- GIVEN 一项工作已重新规划三次，仍收到需要再次重新规划的请求
- WHEN 系统处理该请求
- THEN 工作转为需人处理并记录原因，不再调用规划 agent；原计划版本和失败依据保留

### Requirement: R-orchestration-010 两段控制流与可信规划输入
从接收到规格确认的前段必须来自人工编写且带版本的处理流程，不经执行段规划 agent 生成；规格确认后才允许生成执行段，多层规格每确认一层才生成下一层所需部分。规划输入只允许已确认规格、处理流程、授权记录、执行环境模板、工作基于提交的 Fasfile 与有权限的人的明确指令；工单原文、媒体、评论及外部返回值只能作为不可信数据，不进入规划上下文。
#### Scenario: R-orchestration-010.S1 确认是规划可信边界
- GIVEN 含不可信正文和附件的工单按已版本化流程推进到规格评审
- WHEN 观察确认前的调用记录，再由有权限的人确认该规格版本
- THEN 确认前执行段规划调用数为零；确认后产生独立的已确认规格引用，规划桩只收到允许的可信输入，不含工单、附件或普通评论原文

### Requirement: R-orchestration-011 可信指令与普通消息
有权限的人通过明确请求提出的补充指令必须在步骤之间生效，形成带指令依据的新计划版本并重新校验；同样内容来自无权限的人或普通消息时，只能作为不可信数据交给步骤，不能改变计划。正在运行步骤的结果必须留在原版本。暂停、接管等立即干预不得被混同为普通的重新规划指令。
#### Scenario: R-orchestration-011.S1 相同文字不同授权
- GIVEN agent 步骤正在执行，相同请求分别来自有权限的明确指令和无权限的消息
- WHEN 两条消息被受理并等待当前步骤结束
- THEN 无权限消息只形成不可信数据且不增加计划版本；有权限指令在步骤结束后形成经校验的新版本，旧步骤结果保留，规划输入不含无权限消息

### Requirement: R-orchestration-012 晚到消息交接
交给某个步骤的不可信消息若在该步骤结束后才到达，必须转交同一工作中的下一个 agent 步骤；没有后续 agent 步骤时必须作为待处理事项交给触发人。不能把消息静默留在无人接收的已结束步骤中，也不能因消息内容自行改变控制流。
#### Scenario: R-orchestration-012.S1 步骤结束后的消息不丢失
- GIVEN 目标步骤已经结束，分别存在和不存在后续 agent 步骤
- WHEN 给目标步骤的消息晚到
- THEN 前者在下一 agent 步骤收到该不可信数据，后者生成交给触发人的待处理事项；两种路径均有可追溯记录且不改变计划

### Requirement: R-orchestration-013 不可信输出不能修改计划
agent 步骤输出必须按登记的输出 schema 保留声明字段，未声明字段丢弃并审计后才登记数据引用；不可信数据不能写入计划字段。agent 只能发出请求重新规划的标志，说明文字作为不可信数据保存供人查看，不给规划 agent；新的规划仍只能读取可信输入并重新校验。
#### Scenario: R-orchestration-013.S1 计划形状字段被剥离
- GIVEN agent 输出夹带步骤、评审人或关卡变更字段，并附请求重新规划标志与说明
- WHEN 系统接收输出并处理重新规划请求
- THEN 未声明字段被丢弃并审计，不进入计划；仅重规划标志触发受上限约束的新规划，说明不进入规划上下文，新计划须重新校验

### Requirement: R-orchestration-014 不可变引用版本
步骤之间只传递数据引用，由系统按授权与数据范围解析，不经 LLM 中转数据。引用格式必须为 `ref://<插件>/<类别>/<标识>@<版本>`；数据不可变，版本由内容与标签共同决定。每次引用解析必须检查授权和数据范围并写入审计，拒绝未经授权读取。
#### Scenario: R-orchestration-014.S1 同内容不同标签
- GIVEN 两份内容完全相同但来源、可信度或读取范围标签不同的数据
- WHEN 登记引用并分别由获授权与未获授权的主体解析
- THEN 两份数据版本不同且原内容不可修改；获授权解析成功，未获授权解析被拒绝，每次解析或拒绝均可审计

### Requirement: R-orchestration-015 可信度沿数据流传递
数据必须携带来源、可信度及读取范围标签；agent 产出在人工检查与评审前一律不可信。只要一个输入不可信，步骤输出就必须不可信；系统处理或检查通过本身不能提升可信度。只有人工确认或可信来源能产生已确认数据，确认应新建引用并保留原数据。
#### Scenario: R-orchestration-015.S1 混合输入不提升可信度
- GIVEN 一个步骤同时读取可信输入与不可信 agent 产出
- WHEN 步骤生成结果，随后有权限的人确认该结果
- THEN 步骤原结果仍标为不可信；人工确认形成新的已确认引用，保留确认人及依据，原引用不被覆盖

### Requirement: R-orchestration-016 对外动作按数据标签检查
每次对外动作必须依据所读取数据的标签、授权记录与目标渠道检查策略。内容排除范围内数据不得发给模型厂商，仓库数据不得写往无权访问该仓库的渠道。被拒绝动作必须记录原因与数据引用，不产生对外效果；与其无依赖关系的合法步骤应继续。
#### Scenario: R-orchestration-016.S1 内容排除只阻止违规动作
- GIVEN 一条分支将带内容排除标签的数据发往模型厂商，另一独立分支合法
- WHEN 执行计划
- THEN 违规动作被拒绝并审计，模型桩未收到该数据；独立合法分支完成，依赖被拒绝结果的步骤不得伪装成功

### Requirement: R-orchestration-017 人的消息不受工作队列拥塞阻挡
人的后续消息、评审与状态请求必须独立于工作执行队列受理，再经鉴权和分类送达对应工作、关卡或步骤；工作队列排满不能阻止人推进已有工作。工作队列排满时人的消息必须在五秒内被受理。
#### Scenario: R-orchestration-017.S1 工作排满仍受理消息
- GIVEN 长步骤占满工作执行名额，其他工作仍在排队
- WHEN 向已有工作发送有权限的人的消息
- THEN 消息在五秒内完成受理和路由，此时长步骤仍运行且其他工作仍排队，消息不越过鉴权或分类规则

### Requirement: R-orchestration-018 无副作用回放
必须能依据记录的计划版本、步骤输入与输出引用回放完成的执行。回放时系统步骤重新执行，agent 步骤复用记录输出；各步输入由回放的上游结果重新组装。对外动作必须明确采用回放模式而不产生真实效果，不得把所有历史输出直接复制伪装为回放成功。
#### Scenario: R-orchestration-018.S1 回放结果与原执行一致
- GIVEN 一次完成的执行及完整步骤输入输出记录
- WHEN 对该执行回放
- THEN 系统步骤重新运行，agent 没有新增调用，对外动作有回放标记且效果数不变；每步输出引用与原执行一致，后续步骤使用本次回放产生的上游输出

### Requirement: R-orchestration-019 系统步骤确定性
系统步骤以相同输入运行时必须产生完全相同的业务输出；时间戳、外部流水号等非确定数据只能写入元数据，不能污染输出或引用版本。步骤目录中的每个系统步骤必须通过这一检查才能登记供计划选择。
#### Scenario: R-orchestration-019.S1 逐项验证登记资格
- GIVEN 待登记的全部系统步骤及各自相同输入，其中一项把外部流水号写入业务输出
- WHEN 每项以相同输入执行两次并检查登记资格
- THEN 输出一致的步骤可登记；输出不一致的步骤被拒绝登记并指出差异，非确定元数据不改变业务输出引用

### Requirement: R-orchestration-020 发布与步骤版本兼容
进行中的工作必须继续使用其计划记录的步骤实现版本，新工作才使用升级版本。持久化运行时的应用版本固定为解释器版本，不随处理流程、计划或目录数据变化；兼容修改须保持新旧逻辑可恢复，不兼容修改采用排空发布，旧版本的进行中工作完成后才可下线。
#### Scenario: R-orchestration-020.S1 排空发布并升级步骤实现
- GIVEN 旧版本工作正在执行或等待关卡，准备发布不兼容解释器与新版插件步骤
- WHEN 启动新版本接收新工作，并让旧版本工作继续到完成
- THEN 旧工作可恢复并使用原计划记录的步骤版本，新工作使用新版本；旧进程在其工作全部完成前不得下线，全部排空后才完成发布
