## ADDED Requirements

### Requirement: R-spec-005 工作与规格分层推进
系统必须把已受理工作关联到唯一变更目录、来源工单和基于提交，记录规模、分类依据、模板版本及每层 PR。小改动只有需求层及增量；较大工作依次产生需求、设计、任务层，每层独立 PR，前层获得有效确认并合并后才能产生下一层。完成规格确认只形成可供后续执行使用的版本，不表示工作已完成或已交付代码。
#### Scenario: R-spec-005.S1 大工作逐层推进
- GIVEN 已受理的较大工作已有需求 PR
- WHEN 需求仅批准未合并、批准撤销，或批准且合并
- THEN 前两种情况不能产生设计 PR；最后一种允许产生设计层，且设计到任务遵循同样规则；各层记录可追溯至工作与提交
#### Scenario: R-spec-005.S2 小改动与终点
- GIVEN 已判断为小改动且记录依据的工作
- WHEN 需求及增量通过确认并合并
- THEN 不强制创建空设计或空任务层；记录已确认规格版本，不标记代码交付完成，不启动 M2 节点执行

#### Scenario: R-spec-005.S3 工单变化回到受影响阶段
- GIVEN 已受理工作关联工单及当前规格层
- WHEN 工单关闭或取消，或正文修改影响已起草规格
- THEN 关闭或取消停止后续推进；实质修改记录差异并回到受影响阶段，不沿用失效确认；结束后的 bot 或 CI 消息不能自行唤醒工作

### Requirement: R-spec-006 澄清与规格质量检查
规格正文必须符合现行模板、编号与引用规则。信息不足时须提出一个具体问题，提供可行选项和推荐方案，记录问题、回答与来源；实质待澄清未解决不得提交规格 PR。提交前必须运行已有规格自检和配置检查，并检查验收标准是否可判定；机械格式通过不能替代可判定性检查或人工批准。规格起草结果在人工确认前不可信。
#### Scenario: R-spec-006.S1 缺项阻止提交
- GIVEN 工作存在影响范围或验收的未解决问题
- WHEN 起草步骤尝试提交规格 PR
- THEN 不创建 PR，向有权限的成员发送带选项及推荐的问题，记录等待状态；只有获得明确回答后才能继续，超时不等于同意
#### Scenario: R-spec-006.S2 无效规格与有效修订
- GIVEN 草案含错误编号、断开的覆盖引用或不能判定的 THEN
- WHEN 执行提交前检查并修订草案
- THEN 不合格版本不提交；修订后保留实际 validate/check 结果和可判定性检查依据，再创建对应层 PR，不把 agent 自检视为批准

### Requirement: R-spec-007 评审人与当前版本确认
系统必须按层与授权确定评审人，并加入 Fasfile 所涉事前确认领域的确认人。所有必需确认均须来自有权限且满足职责分离的人，绑定 PR 当前提交；新增提交、撤销批准、请求修改均使不再适用的确认失效。关闭未合并不算确认交付。agent 可以请求评审和报告状态，不能代人批准或合并。
#### Scenario: R-spec-007.S1 领域确认不可遗漏
- GIVEN 需求或设计涉及 Fasfile 规定须事前确认的领域
- WHEN 创建该层 PR 并收到一般评审人的批准
- THEN 自动请求对应领域确认人；领域确认未齐时不推进，全部必需确认及合并完成后才解锁后层
#### Scenario: R-spec-007.S2 确认只对应当前版本
- GIVEN PR 曾在旧提交获得批准
- WHEN 出现新提交、批准撤销、请求修改或关闭未合并
- THEN 旧批准不能确认新版本或推进后层；状态和阻塞原因与 GitHub 当前事实一致，无权用户和 agent 的批准请求被拒绝

### Requirement: R-spec-008 仓库约束的版本与强度
工作必须使用基于提交的 Fasfile、fasrun.yaml 与规格模板版本，解析结果按提交缓存；主分支约束更新只对之后开始的工作生效。Fasfile 只能收紧组织安全策略与执行环境模板，放宽条目必须被拒绝。没有 Fasfile 时仍受组织规范与模板约束。受保护归档内容不能任意改写；已授权系统归档仅允许现有归档动作的移动、增量合并及元数据写入，不形成通用写入豁免。
#### Scenario: R-spec-008.S1 固定提交与拒绝放宽
- GIVEN 旧工作使用提交 A，主分支 B 修改约束，另有放宽组织限制的 Fasfile
- WHEN 继续旧工作、启动新工作并校验放宽版本
- THEN 旧工作仍用 A，新工作用 B；放宽版本拒绝并指出冲突项；无 Fasfile 的仓库仍应用组织和模板约束
#### Scenario: R-spec-008.S2 归档的有限授权
- GIVEN 已归档目录受 protected_paths 保护，另有符合归档前置条件的活跃变更
- WHEN 普通工作试图修改历史归档，或已授权系统调用现有 spec archive
- THEN 普通修改拒绝；系统只可完成既定归档动作，保留现有冲突与覆盖检查，不允许借该权限改写无关历史文件

### Requirement: R-spec-009 工作闭环证据
从工单受理到规格确认必须能查询同一工作中的授权记录、澄清、各层 PR、检查结果、评审及确认版本，向来源工单写回状态和可访问的链接。中断恢复、重复事件与重试不能创建重复工作或 PR。M1 阶段验收必须在专用环境使用真实控制平面、Keycloak/GitHub；澄清及起草 agent 可用可控桩。终点为规格确认及后续执行交接，不以代码合并或归档状态表示；真实接入与模拟回归证据分开记录，不宣称真实自动起草。
#### Scenario: R-spec-009.S1 工单到规格确认可追溯
- GIVEN 专用验证环境的真实控制平面、Keycloak/GitHub，以及真实验证仓库中经准入的工单；澄清和起草 agent 使用记录版本的可控桩，存在一次澄清及需要独立评审的规格层
- WHEN 完成回答、检查、PR 提交及有权限人的当前版本确认与合并
- THEN 可从工作查到认证、授权、澄清、自检及真实 PR/评审/确认提交，真实工单收到对应写回；记录桩版本与模拟部分，没有 M2 执行动作，不宣称真实自动起草或代码完成
#### Scenario: R-spec-009.S2 重试不会重复创建
- GIVEN PR 已创建但本地结果尚未持久化时进程中断
- WHEN 恢复并重放工单事件及提交步骤
- THEN 查询并关联同一 PR，工作、来源及 PR 关联只有一份，原确认证据不丢失

### Requirement: R-spec-010 可替换的 agent 调用契约
澄清与规格起草必须通过可替换的 agent 调用契约接入，调用及结果可关联工作、步骤和版本；结果按声明类型校验、按不可信数据处理，不能直接批准或修改控制流。可控桩须经同一契约提供成功、失败和无效输出，不得绕过持久化、权限、自检或人工关卡。M2 的真实节点、执行器和模型调用链沿用该控制平面与契约接入，M1 不以桩运行宣称真实自动起草。
#### Scenario: R-spec-010.S1 更换实现不改变控制平面规则
- GIVEN 同一工作流程和两种符合契约的可控 agent 实现，分别返回不同内容及一次失败
- WHEN 在专用验证环境切换实现并运行澄清和起草步骤
- THEN 无需替换工作及关卡流程即可接收契约结果；调用与结果关联原工作、步骤和版本，失败如实记录，产出仍须自检和独立人工确认
#### Scenario: R-spec-010.S2 桩不能成为绕过检查的路径
- GIVEN agent 实现返回无效类型、未声明的控制字段或声称已批准的文本
- WHEN 同一调用契约接收结果
- THEN 无效结果不能作为有效规格推进；未声明控制字段按输出规则丢弃并审计，批准文本不推进人工关卡；模拟回归与真实接入记录分别标明所用组件
