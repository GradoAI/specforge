# SF-5 control-plane test resources

Import `@fasrun/test-utils/control-plane` explicitly. Ordinary test-backend consumers do not start DBOS or load its fixture entry point. These are isolated test doubles and resource helpers, not the T013 production runtime or evidence that M1 is complete.

- `createFixtureClock` supplies deterministic timestamps and IDs, independent per fixture. `createFaultInjector` consumes explicitly armed faults at named points.
- `createGitHubFixture` models duplicate/reordered deliveries, current-object reads, 429 with retry-after, effects and response loss. It deliberately creates duplicates on blind retry when the remote system lacks idempotency. Query by marker to exercise reconciliation. No HTTP requests, real installation, secrets or user data are involved; the T009 adapter tests can wrap it in their transport double.
- `createAgentFixture` has two versioned implementations (`controlled-agent-a@1`, `controlled-agent-b@1`) with the same call/attempt interface. Explicitly enable it and supply a response factory that builds the relevant contract envelope. Returned values are **unknown**, including malformed fields: consumers must run their actual schema/auth/taint/approval logic. Success/failure/timeout/cancellation are deterministic. Cancellation cannot overwrite a completed result. This helper does not replace the persistent T011 invoker and claims no real drafting ability.
- `createDbosTestResource(inject('fasrunPostgres'))` clones a fresh test database and generates its own non-superuser, non-BYPASSRLS runtime role. The runtime owns only its `dbos` schema; `fasrun_app` cannot read it. Register SDK workflows before `start()`. `stop()` preserves data for restart; `dispose()` only drops this resource's generated database and role. Do not log ephemeral connection URLs.

DBOS is a process singleton. The helper refuses a second active runtime rather than shutting down somebody else's runtime. Use separate test worker processes for simultaneous runtimes, or stop one before starting another. Do not invoke the SDK lifecycle directly while a resource is active. Registrations survive stop/restart; use unique function names when creating independent resources in one worker. Cloud mode is refused, tracing/export is disabled, and no conductor credentials are configured. Tests use the existing Postgres 18 container and Xinghe assets without changing their fields or adding future business tables.

`TC-SF5-FIXTURE-001` includes deterministic unit cases and a real DBOS/Postgres test: recorded workflow output survives restart without rerunning the completed step; a second database with the same workflow ID is independent; disposing one resource leaves another runtime, template and sentinel database untouched. This is resource verification, not the later TC-CF SIGKILL/full-suite acceptance.
